One important design decision I made was to use Amazon Bedrock AgentCore Gateway as the interface between the customer-support agent and external business systems. Instead of implementing order tracking and refund processing directly inside the agent, I used the Gateway and MCP to expose these capabilities as tools. This separates the agent’s reasoning from the underlying business logic and makes the system easier to maintain and extend. The project instructions specify using the Gateway to expose the order-tracking API and refund-processing Lambda as agent tools.

A concrete challenge I encountered was configuring the AgentCore Gateway targets. The Gateway was successfully created and showed a READY status, but when I checked its targets using the AWS CLI, the result showed an empty list. As a result, the agent could not access the actual order-tracking functionality and instead relied on the Knowledge Base for general order-status information. The project instructions expected the order_tracker and refund_processor tools to be available through the Gateway. I investigated the Gateway configuration and discovered a target-name validation error. I then adjusted the target configuration to comply with the naming requirements of the AWS environment.

For a production environment, I would improve the agent's security, reliability, and observability. The project currently uses the NONE authorizer for the educational environment, so I would implement proper authentication and authorization, least-privilege IAM policies, encryption, and secure secret management. I would also add CloudWatch monitoring, structured logging, tracing, alerts, automated testing, retry and error-handling mechanisms, and human escalation for sensitive operations such as refunds. These improvements would make the agent more secure, reliable, maintainable, and suitable for real-world customer-support workloads.
